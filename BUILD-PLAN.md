### Reading this diagram

The offline half is genuinely finished. The runtime half has every box built —
that is the important thing to internalise before starting. This is not a
half-built system; it is a fully-built system with cut wires.

Three wires are cut, and they all run through the same junction box:
**`macro/guidance.py` is the only place that decides which artistic knobs turn
on, and it currently emits none of them.** `TransitionEngine` gates meter on
`constraints["meter_strictness"]`; `ScoringEngine` reads `priors["meter_preference"]`
and `priors["emotion_alignment"]`. None of those keys are ever written. Every
artistic term in the score is therefore multiplied by zero, and the meter
constraint is skipped on every candidate.

A fourth wire — `RhymeConstraint` — was never connected at either end. It is
constructed in `TransitionEngine.__init__` and exposed through a
`get_rhyme_constraint()` getter that nothing in the codebase calls.

## 2) The metadata boundary (why PR #23 mattered)

This is the single most important structural fact in the project, and it is not
obvious from reading any one file:

```
   apply_tier1_features()  ─┐
   apply_tier2_features()  ─┼──▶ runs inside ChromaStore.build_index()
                            ─┘    ONLY at index time

   data/processed/*.jsonl carries:
       chunk_id, text, tokens, line_id, play, act, scene,
       line_in_scene, word_index, start/end_word_idx, token_count

   data/processed/*.jsonl does NOT carry:
       stress_pattern, rhyme_class, syllable_count, iambic_score,
       emotion_valence, first_token, last_token,
       starts_with_function_word, ends_with_function_word
```

Before PR #23, generation loaded chunks from the JSONL files. So:

- `MeterConstraint.evaluate()` read an empty `stress_pattern` and returned
  `(True, "ok")` — a no-op dressed as a pass.
- `build_scoring_features()` defaulted `iambic_score` and `emotion_valence` to `0.0`.
- `GrammarConstraint` read absent `first_token`/`last_token`/function-word flags,
  so it degraded to an empty-text check.

**Consequence for the builder:** turning on a knob is necessary but never
sufficient. Any feature the constraints read must arrive on the chunk dict, which
means it must come through `CandidatePool`. If you add a new Tier-2 feature, it
has to be added to `tier2_derived.py` **and the index rebuilt**, or it will be
silently absent at runtime. Silently — that is the failure mode this codebase
keeps producing, so assert on it rather than eyeballing it.

## 3) Data flow: generating one beat

```
BEAT GENERATION — current, post-PR-#23
══════════════════════════════════════

PlayPlan beat
     │
     ▼
GuidanceEmitter.guidance_for_beat(beat)
     │  emits: anchor_targets, required_anchor_count, anchor_presence
     │  MISSING: meter_strictness, meter_preference,
     │           length_preference, emotion_alignment          ◀── M1 fixes
     ▼
CandidatePool.for_beat(beat, anchors, exclude_ids=used)
     │  query = objective + rhetorical_mode + anchors
     │  ├──▶ shpoet_lines      ┐
     │  ├──▶ shpoet_phrases    ├─ merge, dedupe by chunk_id,
     │  └──▶ shpoet_fragments  ┘  sort by (distance, chunk_id)
     │
     │  ⚠ returns overlapping chunks: "..._line101" and
     │    "..._line101_p0" are the same words                  ◀── M2 fixes
     ▼
800 candidate chunks, Tier-2 metadata attached
     │
     ▼
BeamSearch.run(guidance, beam_width, max_length, ...)
     │
     │  for each depth, for each beam:
     │      TransitionEngine.enumerate_candidates()
     │          ├─ reuse_lock.is_used(chunk_id)   ⚠ wrong identity  ◀── M2
     │          ├─ grammar.evaluate()             ✓ now has features
     │          ├─ meter.evaluate()               ✗ skipped (knob 0) ◀── M1
     │          └─ anchor.evaluate()              ✓
     │      ScoringEngine.score_candidate()
     │          anchor + length + (meter × 0) + (emotion × 0)   ◀── M1
     │
     │  every checkpoint_interval:
     │      Critic.evaluate_window()  ── real Anthropic call
     ▼
best_path → line_ids → rendered lines
```

### Where this goes wrong today

| Failure | Symptom you would see | Milestone |
|---|---|---|
| No meter knob emitted | Lines scan badly; `meter_score` is 0.0 in every breakdown | M1 |
| No emotion/length knobs | Score is effectively `anchor_hits` alone | M1 |
| Overlapping chunks selectable | The same Shakespeare words appear twice in one play | M2 |
| Rhyme never evaluated | Couplets never form even when the passage calls for one | M4 |
| Replay suite always passes | A green run tells you nothing | M3 |
| Synchronous generation | Browser times out on a real 5-act run | M6 |

### Why `validation/` is its own package (M2)

Quote integrity is not a constraint — constraints prune *candidates during*
search. This is a check on the *finished artifact*: given a rendered play, does
any source word span appear twice? That is a different job, run at a different
time, and it must be able to fail a play the search believed was legal. Keeping
it separate means it can also be pointed at previously-exported plays in
`data/output/` without touching the search path.

### Milestone 1 — Turn on the artistic knobs

**Build:**
- In `macro/guidance.py`, extend `GuidanceEmitter.guidance_for_beat()` to emit:
  - `constraints["meter_strictness"]`
  - `priors["meter_preference"]`, `priors["length_preference"]`,
    `priors["emotion_alignment"]`, `priors["target_valence"]`
- Add matching defaults to `config/settings.py` (`SHPOET_METER_STRICTNESS`,
  `SHPOET_METER_PREFERENCE`, `SHPOET_LENGTH_PREFERENCE`,
  `SHPOET_EMOTION_ALIGNMENT`). **Config-driven, not hardcoded** — this is what
  keeps the knobs-off control group reproducible for M3's A/B.
- Let the beat's `rhetorical_mode` modulate the values where it makes sense
  (a soliloquy can afford stricter meter than a quarrel).

**Why first:** It is the smallest change with the largest effect, it is fully
unblocked by PR #23, and nothing downstream can be evaluated until the signal
under evaluation is non-zero.

**Test:**
- `GuidanceProfile` contains every knob key with a non-zero default.
- `TransitionEngine` actually prunes: `pruned_reasons` contains `meter_clash`
  or `weak_meter_flow` on a corpus where it should.
- `ScoringEngine` breakdown shows a non-zero `meter_score`.
- Existing suite stays green.

**Done when:** A generated beat's score breakdown shows non-zero `meter_score`,
and the transition engine reports meter-based pruning reasons.

**Risks:**
- ⚠ Over-strict meter starves the pool → beam search dead-ends and rolls back
  repeatedly. Start `meter_strictness` low (~0.3) and raise it.
- ⚠ `emotion_valence` is degenerate — **89% of the corpus is exactly 0.0**
  (396,370 of 447,088 chunks). Wire the knob for completeness, but expect it to
  do nothing. Do not read that null result as "emotion doesn't help"; the
  extractor is the problem, not the idea. See M7.

**Estimate:** 1 session

### Milestone 2 — Quote integrity (no-reuse, done properly)

**Build:**
- `CandidatePool`: dedupe on normalized text (case, trailing punctuation) so
  `..._line101` and `..._line101_p0` cannot both occupy pool slots.
- `micro/reuse_lock.py`: key on **source word span**, not `chunk_id`. The
  provenance for this already exists — `line_id` plus `start_word_idx` /
  `end_word_idx` were built for exactly this purpose (`ARCHITECTURE.md` §5.3).
  Marking a chunk used must lock every overlapping span on that source line.
- `validation/quote_integrity.py`: post-generation validator returning structured
  violations (which spans, which beats, which source lines).
- Call the validator at the end of `generate_play` and record the result on the
  generation record.

**Why here:** This is a correctness bug against the project's defining rule —
*"No quote fragment reused anywhere in the generated play"* (`AGENTS.md`). Until
it is fixed, a run that looks good may be invalid, and any quality measurement
taken in M3/M4 would be measuring partly-illegal output. Fix it before you start
trusting numbers.

**Test:**
- Regression: two chunks sharing a source span cannot both be selected.
- Validator flags a hand-built play that reuses a span.
- Validator passes a real generated play.
- Overlap detection is correct at boundaries (adjacent-but-not-overlapping spans
  must remain legal — `0–3` and `4–7` on the same line are fine).

**Done when:** A full generated play passes `quote_integrity` with zero
violations, and the regression test proves overlapping chunks are mutually
exclusive.

**Risks:**
- ⚠ Span locking shrinks the effective corpus faster than chunk locking did —
  every phrase and fragment drawn from a used line dies with it. Expect more
  dead-ends; may require raising `pool_size`.
- ? Does a *sonnet* line and a *play* line that happen to share text count as
  reuse? They have different `line_id`s, so the span rule says no. Confirm that
  matches intent, and note the decision in PROGRESS.md.

**Estimate:** 1–2 sessions

### Milestone 3 — Real evaluation harness

**Build:**
- `learning/metrics.py` — compute a scorecard for a generated play:
  - anchor coverage (per act / per scene, vs. obligations)
  - quote-integrity violations (from M2)
  - meter conformity distribution (mean/median `iambic_score` of chosen lines)
  - line length distribution vs. the ~10-syllable pentameter target
  - source diversity (how many distinct plays contributed)
  - search health: dead-ends, rollbacks, checkpoint count, critic flags
- `learning/replay_suite.py` — **replace the placeholders.** `run_scenario()`
  currently always returns `passed=True` with a warning, so a green suite means
  nothing. Wire fixed scenarios through a real generation and assert on metrics.
- Persist scorecards as JSON under `data/eval/` keyed by run config.
- Support running the same scenario with knobs off vs. on for a clean A/B.

**Why here:** M1 and M2 change output quality. Without measurement you are
guessing, and the existing suite actively lies. Build the ruler before measuring.

**Test:**
- Metrics are correct on a hand-built play with known properties.
- The suite fails when handed a play with a seeded regression.
- A/B mode produces two comparable scorecards from one command.

**Done when:** `python -m shpoet.learning.replay_suite` prints a real scorecard,
writes it to `data/eval/`, and returns non-zero on a seeded regression.

**Risks:**
- ⚠ Real scenarios call the Anthropic critic — costs money per run. Provide a
  `--no-critic` flag for fast iteration.
- ? Some quality is genuinely subjective. Keep metrics mechanical; leave the
  aesthetic judgment to reading the output in the composer.

**Estimate:** 2 sessions

### Milestone 4 — First quality runs and tuning

**Build:**
- Full 5-act generation against the real corpus with the real critic.
- Tune, in this order: `pool_size` → `beam_width` → knob weights →
  `checkpoint_interval`.
- Decide `RhymeConstraint`'s fate: wire it into the transition/scoring path for
  passages that call for it, or delete it and its getter. **Do not leave a third
  constraint sitting unreachable.**
- Record every finding in `PROGRESS.md`; promote durable lessons to
  `REVIEW-NOTES.md`.

**Why here:** This is the milestone that answers your actual question — does the
constrained-search approach produce better verse than the baseline? Everything
before it exists to make this measurement trustworthy.

**Test:** A/B scorecards from M3, knobs-off vs. knobs-on, same plan and seed.

**Done when:** A full 5-act play generates end to end, passes quote integrity,
and beats the knobs-off baseline on anchor coverage and meter conformity without
collapsing source diversity.

**Risks:**
- ⚠ Runtime. Per-beat retrieval is ~1.2–2.5s; a 5-act play is many beats, plus
  critic calls. Time one act first and extrapolate before launching a full run.
- ⚠ Corpus exhaustion under span-based reuse (M2) in later acts. Watch for
  rising rollback counts as the play progresses.
- ? Optimal `pool_size` is unknown — 800 is a starting guess, not a result.

**Estimate:** 2–3 sessions

### Milestone 6 — Long-run ergonomics

**Build:**
- Move generation to a background job; `POST /generate` returns immediately with
  a job id.
- Real incremental status on `GET /generate/{job_id}` — beats completed, current
  act/scene, partial lines.
- Composer polls (or consumes SSE) and shows progress during the run.

**Why last of the active work:** Only worth building once runs are long enough to
need it, and M4 will tell you how long that is. Do not pre-optimise this.

**Test:** A full 5-act run does not block the HTTP request; the composer shows
lines arriving; a browser refresh mid-run recovers state.

**Done when:** A complete 5-act generation is watchable start to finish in the
browser without a timeout.

**Risks:**
- ⚠ If you go the SSE route, read the `sse-streaming` skill first — JSON-encode
  the data field. Shakespeare text contains `\n\n` between speeches, which will
  silently truncate raw SSE messages.
- ? In-process background task vs. a real queue. Start in-process; the
  architecture is already noted as queue-ready (`ARCHITECTURE.md` §5.13).

**Estimate:** 2 sessions

### Milestone 7 — Deferred: signal quality and learning

Not scheduled. Pick up when M1–M6 are done and the system is producing plays
worth improving.

- **Fix `features/semantics.py` valence.** 89% of the corpus scores exactly 0.0.
  Until this improves, the emotion knob is decorative. Requires a re-index —
  budget the embedding cost, though `EmbeddingCache` means vectors are not
  re-paid for, only metadata recomputed.
- **Decide `features/tier3_lazy.py`'s fate.** 260 lines, imported by nothing, not
  exported from `features/__init__.py`, no tests. `ARCHITECTURE.md` §5.4 says
  Tier-3 should be "fine meter scans, deeper syntax role, multi-line cohesion,
  computed for candidate pools then cached" — but what was built is generic spaCy
  NLP (dependency trees, NER, noun phrases). Either rewrite it to the spec and
  call it from `CandidatePool`, or delete it. **Dead code that looks load-bearing
  is worse than no code** — it is what made the Tier-3 work look done.
- **Build `learning/updater.py`.** Specified in `ARCHITECTURE.md` §5.12, never
  written: winner/loser weight deltas, avoid-signature penalties, slow learning
  rates. Only meaningful once M3's metrics can tell a winner from a loser.

## 8) Conventions for the builder

- **Branch per milestone**, cut fresh from `main`: `claude-<goal>`. One PR per
  milestone. Never push to `main`, never self-merge.
- **Update `PROGRESS.md` after every commit** — timestamp (America/New_York),
  what changed, next steps, risks. Additive; never rewrite history. This log is
  the project's memory across sessions, and a gap in it is what made the state of
  this project unrecoverable without a full audit.
- **Run the full suite before calling a milestone done.** `venv/Scripts/python.exe -m pytest -q`
- **Never chain shell commands** with `&&`, `||`, or `;` — one call each.
- **Assert on features, don't eyeball them.** This codebase's characteristic
  failure is silent absence: a missing metadata key becomes a `0.0` default,
  a mismatched dimension becomes an empty pool, a placeholder returns
  `passed=True`. When you wire something, add a test that fails if it silently
  stops working.
- Type hints everywhere; comment the *why*; catch specific exceptions.
